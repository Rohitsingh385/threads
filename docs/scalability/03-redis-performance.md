Sprint 3 focused on understanding and validating Redis as a distributed performance and reliability layer for the Threads application, continuing the same scalability investigation established in Sprint 1 and Sprint 2 rather than treating Redis simply as a feature to add. We started by examining why caching exists and how Redis fits into the architecture: PostgreSQL remains the durable source of truth, while Redis is used to reduce repeated database work and provide shared state for features such as feed caching and rate limiting. We investigated Redis fundamentals including memory usage, keys, values, TTLs, latency, key cardinality, value size, and eviction, then traced the application's existing cache-aside implementation for the home feed. The feed cache uses keys in the form `feed:user:{userId}:cursor:{cursor}:limit:{limit}`, meaning that different users, cursors, and page sizes can produce different cached entries. To validate the behavior rather than assuming the cache was working, we started with an empty Redis database using `FLUSHDB`, confirmed `DBSIZE = 0`, executed authenticated k6 requests against `/user/feed`, and verified that Redis subsequently contained the expected feed cache key. We inspected the actual cached value and confirmed that Redis was storing the thread IDs, `nextCursor`, and `hasNextPage`, while also verifying the TTL directly; one cold-cache run produced an average HTTP latency of **24.48 ms**, median **11.82 ms**, p95 **27.4 ms**, and 0% HTTP errors across 20 requests, while subsequent warmed-cache runs produced an average of **13.45 ms** with p95 **19.4 ms**, and another run produced an average of **18.48 ms** with p95 **32.21 ms**. These small localhost measurements are not treated as production capacity numbers, but they demonstrate the expected cache-aside behavior: the initial request can populate Redis and subsequent requests can reuse the cached feed result instead of repeatedly performing the same feed computation. We also observed a cached feed TTL of approximately **62 seconds** during testing, confirming that cached data is intentionally temporary rather than permanent. We then investigated cache invalidation and freshness by examining what happens when cached entries expire and by studying the scalability implications of the current key structure. This led into cache stampede, cache penetration, and cache avalanche scenarios: for example, if a popular feed key expires while thousands of requests arrive simultaneously, all of those requests could miss Redis and fall through to PostgreSQL, potentially creating a sudden database load spike. We deliberately did not add unnecessary distributed locking or complex anti-stampede infrastructure because the current project scope does not provide evidence that such complexity is justified, but we documented the behavior as an important scaling concern. We then investigated Redis failure behavior by deliberately stopping the Redis container and sending requests through the application. The backend correctly detected the Redis connection failure (`ECONNREFUSED 127.0.0.1:6379`) and logged that it would continue without Redis, reinforcing the intended architecture that Redis is an optimization/shared-state layer rather than the source of truth. During this investigation we also encountered a configuration/client-handling issue where the application initially returned **“The client is closed”** after Redis had been stopped; this was traced to the development environment/configuration rather than being accepted as correct failure behavior, and after correcting the environment configuration we verified the intended Redis-unavailable behavior. We next investigated Redis memory behavior rather than assuming that Redis could grow indefinitely. We inspected actual Redis memory statistics and observed roughly **1.2–1.7 MB** of used memory during the experiments, including Redis overhead and dataset memory. We deliberately configured Redis with a **2 MB maxmemory limit** and the **allkeys-LRU** eviction policy to understand how constrained memory behaves, then generated additional cache entries and observed the dataset reaching approximately **431 keys and 1.74 MB** of used memory. During the tested workload, `evicted_keys` remained **0**, so we did not claim that the experiment successfully triggered eviction; instead, the result established how Redis was configured for eviction and showed that the workload used in this experiment did not create sufficient pressure to force eviction. This distinction was important because the goal was to measure actual behavior rather than manufacture an optimization result. Finally, we investigated the Redis-backed fixed-window rate limiter under concurrent load using k6. After correcting an initial test endpoint/environment issue, we ran **20 VUs with 20 iterations** and observed both successful and rate-limited requests, with the final test producing **5 HTTP 200 responses and 15 HTTP 429 responses**, demonstrating that the Redis-backed limiter was enforcing the configured request threshold under concurrent traffic. We inspected the corresponding Redis rate-limit keys and verified their counters and TTLs directly, confirming that Redis was maintaining the shared request state used by the limiter. Across the sprint, the important result was therefore not simply that “Redis makes the application faster”; instead, we established through direct experiments how Redis changes the system's behavior under normal operation, repeated reads, expiration, memory pressure, failure, and concurrent rate limiting. The feed experiments demonstrated cache-aside behavior and reduced repeated work on warmed requests, the TTL experiments established that cached data is temporary, the key inspection showed how cache cardinality grows with the cache-key dimensions, the failure experiment established Redis as a non-authoritative dependency that the application can operate without when correctly configured, the memory experiment demonstrated Redis's memory and eviction configuration without overstating the results, and the rate-limit benchmark demonstrated Redis's role as shared state under concurrent requests. Sprint 3 therefore extends the scalability investigation from PostgreSQL into the caching and distributed-state layer: **Sprint 1 established the workload and baseline, Sprint 2 investigated PostgreSQL query execution, indexing, connection pooling and concurrency, and Sprint 3 investigated whether Redis can reduce database work while also identifying the new scalability and reliability concerns introduced by caching itself—TTL, invalidation, key cardinality, stampedes, memory growth, eviction, Redis failure, and concurrent rate limiting.** The overall approach remains the same throughout the project: establish a measurable baseline, identify a potential bottleneck, test the system under controlled conditions, inspect the underlying behavior, record actual latency and error measurements, and only introduce additional complexity when the evidence shows that it is necessary.

In Sprint 5, we made the Threads API capable of running multiple instances safely and learned how horizontal scaling works in practice. We first understood the difference between vertical and horizontal scaling and why a single Node.js process is limited, then examined the state in our application JWT authentication, Redis, PostgreSQL, uploads, and process memory and ensured that important application state is kept outside an individual Node process so multiple instances can operate independently. We ran multiple API instances on different ports/PIDs and placed Nginx in front of them as a load balancer, verifying that requests were distributed across the instances. We also examined database connection pools and understood how multiple API instances can multiply PostgreSQL connections and potentially create a database bottleneck. We added health/readiness checks to distinguish between a running Node process and an instance that can actually reach PostgreSQL, implemented graceful shutdown using SIGINT/SIGTERM so an instance stops accepting new requests, finishes existing requests, disconnects Prisma and Redis, and then exits cleanly, and tested instance failure to verify that the remaining API instance could continue serving traffic. Finally, we benchmarked the feed API through Nginx using k6 with 1, 2, and 3 API instances. The benchmark showed that adding instances did not produce linear throughput improvement on our single-machine setup, but latency improved significantly from a p95 of 166 ms with one instance to 56 ms with two and 47 ms with three demonstrating that horizontal scaling improves application layer capacity/latency only when shared resources such as PostgreSQL, Redis, CPU, memory, and the network are not already the bottleneck.

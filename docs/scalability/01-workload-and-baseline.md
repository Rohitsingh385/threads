The purpose of this sprint was to understand that “supporting 1 million users” is not itself a meaningful performance requirement because the number of registered users does not directly determine the load placed on a backend; what matters is the actual workload generated by those users, including how many are active, how many requests they generate, how those requests are distributed across the day, which endpoints they use, the read/write ratio, concurrency, peak traffic, and the amount of data involved. For our Threads application, we therefore treated 1M registered users as a long-term scale scenario and defined a representative workload around active users, peak-hour traffic, concurrent activity and API requests rather than claiming that the current system can literally serve one million users. We identified the important journeys in the application—authentication, feed retrieval, viewing threads, creating threads, likes, comments, follows, search, bookmarks and notifications—and reviewed how these requests travel through the existing architecture: the request enters Express, passes through middleware such as authentication, validation and rate limiting, reaches the controller, then the service layer performs business logic and communicates with PostgreSQL through Prisma, Redis where caching/rate limiting is involved, and external services where applicable. We also learned that performance testing requires realistic data because an application behaving well with a handful of users and threads tells us very little about how database queries, indexes and caching will behave with a much larger dataset, so we created a dedicated benchmark data-generation setup rather than modifying the normal development seed, progressively tested large user insertion workloads, and learned that generating data and inserting data are different costs and that batching does not automatically make database insertion faster. We then introduced k6 to generate controlled HTTP traffic and learned the difference between virtual users, iterations, requests per second, concurrency, throughput and latency; importantly, we used a constant-arrival-rate test so that the benchmark specified the traffic we wanted to send rather than simply creating an arbitrary number of concurrent users. Before testing the real feed endpoint, we verified the load-testing setup against the health endpoint, then moved to the authenticated feed endpoint using a dedicated benchmark user and local PostgreSQL and Redis so that the benchmark would not depend on hosted infrastructure. During this process we also encountered a real debugging issue where benchmark middleware was not calling `next()`, which caused requests not to complete; fixing that demonstrated an important practical lesson that load testing is only meaningful when the complete request lifecycle is actually functioning. Once the environment was working, we established a baseline by testing the feed at progressively higher arrival rates for 30 seconds each. At 10 RPS we completed 300 requests with 0% HTTP failures and a p95 latency of 40.06 ms; at 25 RPS we completed 750 requests with 0% failures and a p95 of 22.16 ms; at 50 RPS we completed 1,501 requests with 0% failures and a p95 of 24.02 ms; and at the 100 RPS target we completed 2,776 requests at an actual throughput of 92.53 RPS, with 0% HTTP failures but 224 dropped iterations, p95 latency of 71.07 ms and a maximum latency of about 1.3 seconds. The important lesson from the final test is that zero HTTP errors does not necessarily mean the system successfully sustained the requested workload: at 100 RPS, k6 could not maintain the requested arrival rate, had to increase the number of virtual users, and eventually dropped iterations, which means the system/load-generator combination was beginning to experience pressure even though completed requests were still returning successfully. Conversely, the 10, 25 and 50 RPS tests sustained their requested arrival rates without dropped iterations, so within this specific local benchmark environment the application showed stable behavior through 50 RPS, while 100 RPS exposed the beginning of throughput and tail-latency degradation. We also learned that a benchmark result is not the same thing as absolute system capacity: these measurements were taken on a local development environment with a particular dataset, machine, PostgreSQL instance, Redis instance, application configuration and 30-second workload, so we should not claim that “the application supports exactly 50 RPS” or that “100 RPS is its maximum”; the correct conclusion is that this benchmark established a reproducible baseline under a defined workload. The central engineering method we established in this sprint is therefore BASELINE → CHANGE → TEST → COMPARE: first measure the existing system, then make one meaningful architectural or database change, run the same workload again, and compare latency, throughput and errors against the original baseline. This gives us an experimental way to understand scalability instead of making theoretical claims. Sprint 1 therefore established the workload model, benchmark dataset, load-testing methodology, critical application paths, architecture under test and first performance baseline; the next stage is to investigate where the observed pressure comes from, beginning with PostgreSQL query execution, indexes, query plans and connection behavior, while preserving this baseline so that every optimization can be measured against it.

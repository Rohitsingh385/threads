Sprint 2 focused on understanding and validating the PostgreSQL layer of the Threads application rather than forcing an artificial optimization. We first traced the real SQL queries generated by Prisma for the `/user/feed` endpoint and identified the sequence of database operations involved in loading follows, threads, and the current user's likes. We then used `EXPLAIN` and `EXPLAIN ANALYZE` against a large benchmark dataset of 100K users and 500K threads to understand PostgreSQL query planning, sequential scans, index scans, bitmap scans, sorting, index-only scans, and the leftmost-prefix behavior of composite B-tree indexes. The existing `Thread(authorId, createdAt)` index was verified to be useful for author-based feed queries, while PostgreSQL correctly chose sequential or parallel scans for workloads where those plans were cheaper, demonstrating that an index is not automatically better. We also tested feed-like queries with different follower fan-outs and observed PostgreSQL changing from repeated index lookups to a hash join and parallel sequential scan as the number of followed users increased, showing that query plans are workload-dependent. We investigated Prisma/PostgreSQL connection pooling by examining active database connections and using a temporary `pg_sleep()` endpoint with a restricted connection pool, demonstrating that pool contention can increase request latency and that connection requirements multiply as application instances scale horizontally. We reviewed the application's transaction usage for likes, including atomic creation/deletion of Like records, denormalized `likesCount` updates, and notification creation, and studied ACID properties, transaction duration, row-level locking, deadlocks, isolation levels, and concurrency concerns. We also examined denormalized counters such as `likesCount`, `commentsCount`, `followerCount`, and `followingCount`, identifying the underlying relational tables as the source of truth and transactions as the mechanism used to keep counters consistent with writes. Finally, we repeated the feed benchmark using the same constant-arrival-rate methodology as Sprint 1: at 10 RPS the system achieved 10.02 RPS with 0% HTTP errors and a 52.12 ms p95; at 50 RPS it achieved 47.31 RPS with 0% HTTP errors, 53.55 ms p95, and 81 dropped iterations; and at 100 RPS it achieved 91.45 RPS with 0% HTTP errors, 243.08 ms p95, and 253 dropped iterations. The final conclusion is that the PostgreSQL investigation did not provide sufficient evidence to justify changing the existing indexing or query structure; instead, the benchmark established that higher arrival rates produce increasing tail latency and dropped iterations while the requests that were actually executed continued to complete without HTTP errors. Sprint 2 therefore produced a measured understanding of PostgreSQL query execution, indexing, connection pooling, transactions, concurrency, counters, and workload behavior rather than an artificial code change.
